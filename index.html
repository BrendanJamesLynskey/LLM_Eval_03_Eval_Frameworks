The Framework Landscape

The LLM eval framework space has fragmented into three overlapping categories. Understanding which category solves your problem prevents tool sprawl.

Safety-focused
Inspect AI HarmBench AISI Tasksets
Production eval
Braintrust Langfuse Weights & Biases Weave Arize
Obs + eval
Phoenix (Arize) Langsmith Helicone
CI / unit
deepeval OpenAI Evals ragas promptfoo
Selection heuristic

If your primary concern is safety and agent capability benchmarking: Inspect AI. If it is production monitoring + experiment tracking: Braintrust or Langfuse. If it is distributed tracing + lightweight eval: Phoenix. If it is CI/CD regression gating: deepeval or promptfoo. If you are evaluating OpenAI models and want no infrastructure: OpenAI Evals harness.

All six frameworks support Python. Four have TypeScript SDKs. Only Phoenix is OpenTelemetry-native. Braintrust and Langfuse have proprietary trace formats but both export to OTLP via adapters. Inspect AI and deepeval are fundamentally offline eval runners; the others include online observability components.

02

Inspect AI (UK AISI) — Agent Evals, Sandboxed Tools, Scorers

Inspect AI (inspect_ai v0.3+, Python ≥ 3.10) is the UK AI Safety Institute's open-source framework for rigorous capability and safety evaluation. Its design prioritises reproducibility, sandboxed tool execution, and composable scorers.

inspect_ai — minimal task definition
from inspect_ai import task, eval
from inspect_ai.dataset import json_dataset
from inspect_ai.scorer import model_graded_fact, exact
from inspect_ai.solver import generate, chain_of_thought
from inspect_ai.model  import get_model

@task
def my_eval():
    return {
        "dataset": json_dataset("evals/factual_qa.jsonl"),
        "solver":  [chain_of_thought(), generate()],
        "scorer":  model_graded_fact(model="anthropic/claude-3-5-sonnet-20241022"),
    }

# Run:  inspect eval my_task.py --model anthropic/claude-3-opus-20240229

Key features

Sandboxed tool execution

Agent evals requiring bash or Python execution run inside Docker containers (sandbox="docker") or local processes (sandbox="local"). Each sample gets a fresh sandbox. Prevents side-effects from contaminating other samples. Supports inspect sandbox exec CLI for debugging.

Composable scorers

Built-in: exact, includes, regex, model_graded_fact, model_graded_qa, pattern. Custom scorers are Python callables returning Score(value, answer, explanation). Multiple scorers can be stacked; results are stored per-scorer in the log file.

AISI use in practice

AISI used Inspect AI for the UK Government's frontier model evaluations (GPT-4o, Gemini Ultra, Claude 3 Opus) published in 2024. The framework runs on their HPC cluster with parallelism via async samplers. Output is a structured .eval log file that can be opened in the Inspect AI web viewer for drill-down review.

Braintrust — Production-Focused, Datasets, Online Evals

Braintrust is a commercial eval platform focused on experiment tracking and online evaluation of production traffic. SDK: braintrust (Python & TypeScript). It wraps the OpenAI client pattern to enable zero-friction instrumentation.

braintrust — offline experiment
import braintrust
from braintrust import Eval
from autoevals import Factuality, Battle  # braintrust's scorer lib

await Eval(
    "my-project",
    data=lambda: [
        {"input": "Explain RLHF", "expected": "reinforcement learning from human feedback..."},
    ],
    task=lambda x: anthropic_client.complete(x["input"]),
    scores=[Factuality, Battle],
    experiment_name="claude-3-5-sonnet-v2",
)

Online eval (production tracing)

braintrust — production span logging
with braintrust.start_span("query") as span:
    response = client.chat_completions_create(...)
    span.log(
        input=user_query,
        output=response.content,
        expected=None,  # filled later by human review
        scores={"latency_ms": response.latency()},
    )

Braintrust stores traces in its hosted backend. Experiment results are versioned and diffed automatically against the baseline experiment. The UI shows score distributions, regressions highlighted in red, and allows human annotators to add labels directly in the browser.

autoevals library

autoevals (open-source, bundled with Braintrust) provides Factuality, Battle, ClosedQA, Summary, Moderation, SQLScorer and more, all as composable callables with known calibration data. Can be used standalone without Braintrust cloud.

Phoenix (Arize) — OSS, OTel-Native, Trace & Eval

Arize Phoenix (arize-phoenix v4+) is an open-source, OpenTelemetry-native observability + eval platform. It stores traces in a local SQLite or Postgres database and exposes a browser UI on localhost:6006 by default. No cloud account required.

phoenix — instrument an Anthropic client
import phoenix as px
from openinference.instrumentation.anthropic import AnthropicInstrumentor
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter

px.launch_app()  # starts local UI at http://localhost:6006

provider = TracerProvider()
provider.add_span_processor(
    SimpleSpanProcessor(OTLPSpanExporter(endpoint="http://localhost:6006/v1/traces"))
)
trace.set_tracer_provider(provider)
AnthropicInstrumentor().instrument()  # auto-traces all anthropic calls

Running evals on collected traces

phoenix — LLM-as-judge on trace dataset
from phoenix.evals import llm_classify, OpenAIModel
import pandas as pd

traces_df = px.Client().get_spans_dataframe()  # pull from local store
eval_df = llm_classify(
    dataframe=traces_df,
    model=OpenAIModel(model="gpt-4o"),
    template="hallucination",  # built-in template
    rails=["factual", "hallucinated"],
    concurrency=10,
)
OTel semantic conventions

Phoenix uses the OpenInference semantic conventions (openinference-semantic-conventions package) to define span attributes like llm.input_messages, llm.output_messages, llm.token_count.total. These are a superset of the upstream OTel semantic conventions for GenAI. Any instrumentation library that emits OpenInference spans works with Phoenix out of the box, including openinference-instrumentation-langchain and -llamaindex.

Langfuse — Observability & Eval Bundled

Langfuse (langfuse v2+) is an open-source (MIT) LLM observability + eval platform. Self-hostable via Docker Compose or available as a managed cloud. Its data model uses traces → spans → observations (hierarchical), with first-class scores attached to any node.

langfuse — tracing + scoring
from langfuse import Langfuse
from langfuse.decorators import observe, langfuse_context

lf = Langfuse(public_key="...", secret_key="...", host="https://cloud.langfuse.com")

@observe()
def run_pipeline(question: str) -> str:
    answer = anthropic_client.complete(question)
    # Attach an inline score — e.g. from a fast classifier
    langfuse_context.score_current_observation(
        name="toxicity",
        value=toxicity_classifier.score(answer),
        data_type="NUMERIC",
    )
    return answer

Eval-specific features

  • Dataset versioning — create eval datasets in the UI; link dataset items to trace observations for side-by-side comparison.
  • LLM-as-judge integration — define judge prompts in the UI; Langfuse runs them asynchronously against sampled traces without touching your application code.
  • Human annotation queues — route uncertain-score items to a named annotation queue; annotators work in the browser; scores written back to the trace.
  • Prompt management — versioned prompt registry with A/B testing support; links prompt version to trace for regression attribution.
Self-hosting vs cloud

Self-host with docker compose up using the official langfuse/langfuse image. Requires Postgres (included in compose). For production, add Redis for queue. Data stays on-prem. The cloud version adds managed infra and SOC 2 compliance. Both use the same SDK; switch by changing the host parameter.

OpenAI Evals — Model-Graded, Simple Harness

The evals library (github.com/openai/evals, Python ≥ 3.9) is OpenAI's own eval harness. It is intentionally minimal: YAML task definitions, a registry-based runner, and a set of built-in model-graded eval types. No UI; output is jsonl log files.

evals — YAML task definition
# evals/registry/evals/my_factual_eval.yaml
my_factual_eval:
  id: my_factual_eval.v1
  description: Factual QA on LLM architecture topics
  metrics: [accuracy]

my_factual_eval.v1:
  class: evals.elsuite.modelgraded.classify:ModelBasedClassify
  args:
    samples_jsonl: evals/registry/data/my_factual/samples.jsonl
    eval_type: fact
    modelgraded_spec: fact
Running an eval
# Run against gpt-4o
oaieval gpt-4o my_factual_eval

# Run against a completions endpoint (custom model)
oaieval gpt-4o my_factual_eval \
  --completion_fn langchain/chat_anthropic:claude-3-5-sonnet-20241022"

Built-in eval types

Model-graded types

  • fact — is the answer factually consistent?
  • closedqa — does the answer satisfy the question?
  • battle — pairwise preference
  • classify — classifies response into a set of labels

Deterministic types

  • match — exact string match
  • includes — substring present
  • fuzzy_match — ROUGE-L above threshold
  • Custom: subclass evals.eval.Eval

deepeval — Pytest-Style Assertions

deepeval (deepeval v1+, Python ≥ 3.8) integrates LLM eval into the standard pytest workflow. The key abstraction is a metric object that you assert against, just like a standard assertion in a unit test. It runs inside pytest, reports pass/fail per test case, and integrates with CI via pytest --tb=short.

deepeval — pytest integration
import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import (
    AnswerRelevancyMetric,
    FaithfulnessMetric,
    HallucinationMetric,
    GEval,
)

@pytest.mark.parametrize("test_case", load_dataset("rag_qa.jsonl"))
def test_rag_pipeline(test_case):
    tc = LLMTestCase(
        input=test_case["query"],
        actual_output=rag_pipeline.query(test_case["query"]),
        retrieval_context=test_case["context_chunks"],
        expected_output=test_case["expected"],
    )
    assert_test(tc, metrics=[
        AnswerRelevancyMetric(threshold=0.7),   # is answer relevant to query?
        FaithfulnessMetric(threshold=0.8),      # is answer faithful to context?
        HallucinationMetric(threshold=0.1),    # hallucination rate < 10%
    ])

Notable metrics

Metric classWhat it measuresUses LLM judge
AnswerRelevancyMetricIs the output relevant to the input?Yes (GPT-4o or configurable)
FaithfulnessMetricAre all claims in output grounded in retrieval context?Yes
HallucinationMetricFraction of output claims that are hallucinatedYes
ContextualRecallMetricFraction of expected answer covered by retrievalYes
GEvalCustom rubric-based eval — define your own criteriaYes (configurable)
ToxicityMetricToxicity score via Detoxify or judgeOptional

Common stack combinations

Safety team: Inspect AI for structured evals + Langfuse for production traces. MLOps / production team: Langfuse or Braintrust for traces + deepeval in CI. Research team: Inspect AI standalone. Data-privacy-constrained: Phoenix + deepeval, fully self-hosted with zero external calls.

09

What to Take Away

  • No single framework covers everything. Offline capability evals (Inspect AI), production tracing (Langfuse/Braintrust/Phoenix), and CI regression (deepeval) address different parts of the eval lifecycle.
  • Inspect AI is the safety benchmark standard. If you need reproducible, sandboxed, government-grade capability evals, it is the current best-in-class.
  • Phoenix is the OTel-native choice. If your stack already emits OTel traces, Phoenix adds eval with zero additional instrumentation.
  • Langfuse + deepeval is the practical OSS stack for teams wanting production monitoring and CI regression gating without cloud vendor lock-in.
  • Braintrust excels at experiment tracking and is the easiest tool to get pairwise eval results into a shared UI quickly.
  • deepeval in pytest is the lowest-friction path to getting LLM quality gates into an existing CI/CD pipeline — no new infrastructure needed.
  • OTel matters long-term. The industry is converging on OpenTelemetry for LLM observability. Pick tools that emit or consume OTLP to stay migration-safe.
